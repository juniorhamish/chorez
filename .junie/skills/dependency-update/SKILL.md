# Dependency Update

This skill turns "keep the project's npm dependencies current" into a repeatable, verified
workflow: detect what's outdated, update `package.json` (and the lockfile) to the recommended
versions, then prove nothing broke — build, lint, unit tests, and a real, logged-in load of the
app in a browser via the Chrome DevTools MCP server.

## Step 1 — Detect outdated packages

Run `npm outdated` from the project root. It prints a table with `Current`, `Wanted`, and `Latest`
columns per package:

- `Wanted` — the highest version satisfying the existing semver range in `package.json` (a safe,
  non-breaking bump).
- `Latest` — the newest version published, regardless of the current range (may cross a major
  version and include breaking changes).

Exit code `1` from `npm outdated` just means "packages are outdated" — that's the expected,
non-error case here; don't treat it as a failed command.

## Step 2 — Classify each package before touching anything

For every outdated package, compare `Current` → `Latest`:

- **Same major version** (e.g. `16.3.0` → `16.3.3`): safe, routine bump.
- **Major version bump** (e.g. `eslint` 9 → 10, `typescript` 6 → 7, `framer-motion` 12 → 13):
  treat as higher-risk. Before updating, check the package's changelog/release notes for breaking
  changes. This repo already runs on pre-release/bleeding-edge majors of several packages (Next.js
  16, React 19, Tailwind v4) — per `AGENTS.md`'s banner, **read
  `node_modules/next/dist/docs/` before changing anything Next.js-related**, since its APIs may
  differ from training data. Apply the same "read the installed package's own docs/changelog
  first" caution to any other major bump you take.

Default to updating every package to `Latest` (that's what "the latest version being
recommended" means here), but call out major bumps to the user before applying them if they touch
a package with security-, auth-, or framework-critical surface (`next`, `@auth0/nextjs-auth0`,
`eslint`, `typescript`) so they can veto one if needed.

## Step 3 — Apply the updates

Update `package.json` directly (don't hand-edit version ranges without reinstalling) using:

```bash
npm install <package>@latest --save          # dependencies
npm install <package>@latest --save-dev       # devDependencies
```

Or update everything at once and let `package-lock.json` regenerate:

```bash
npm outdated --json   # capture the list programmatically if updating in bulk
npm update             # bumps within existing semver ranges (the "Wanted" column)
```

`npm update` alone won't cross major versions (it respects the `^`/`~` in `package.json`), so for
any package where `Latest` is a major bump, install it explicitly with the command above — this
also rewrites the `^`/`~` range in `package.json` to match. Always let `package-lock.json` be
regenerated by these commands rather than editing it by hand. Re-run `npm outdated` afterward —
it should report nothing left (or only packages you deliberately deferred).

## Step 4 — Verify the app still works (build / lint / test)

Run, in order, and fix any failure before moving on (assume failures are caused by the version
bumps until proven otherwise — check the failing package's release notes for the specific
breaking change):

```bash
npm run lint
npm test
npm run build
```

All three must pass. If a major bump breaks one of them, either fix the resulting code (preferred)
or, if the fix is out of scope, revert just that package's bump and note it to the user as
deferred — don't silently skip a failing check.

## Step 5 — Verify the running app in a real browser

Static checks don't catch runtime-only regressions (e.g. a UI library changing its DOM output, or
an auth SDK changing its cookie/session handling). This project has the Chrome DevTools MCP server
available (`mcp_chrome-devtools_*` tools) specifically for this kind of live verification — use it
instead of asking the user to check manually:

1. Start the dev server (`npm run dev`) in the background.
2. Use `mcp_chrome-devtools_new_page` (or `navigate_page`) to open the app's local URL.
3. Take a snapshot (`mcp_chrome-devtools_take_snapshot`) to confirm the landing page renders
   without console errors (`mcp_chrome-devtools_list_console_messages`).
4. Log in through the real Auth0 flow to reach `/dashboard`. This requires a real test account —
   read `TEST_USER_EMAIL` / `TEST_USER_PASSWORD` from `.env.local` (a dedicated Auth0 test account
   kept there specifically for this purpose; it's git-ignored, so it's safe to store real
   credentials in it). Only if those variables are missing, **ask the user to provide test
   credentials** and offer to save them into `.env.local` (as `TEST_USER_EMAIL` /
   `TEST_USER_PASSWORD`, following the placeholders already documented in
   `.env.local.example`) so future runs of this skill don't need to ask again. Never fabricate or
   guess credentials. Drive the Auth0 login form with `mcp_chrome-devtools_fill_form` / `click`.
5. Once on `/dashboard`, snapshot the page again and check the console for errors, confirming
   core UI (task list, header, week strip) rendered correctly post-upgrade.
6. Stop the dev server when done.

If no test account is available (missing from `.env.local` and the user declines to provide one),
at minimum verify the unauthenticated landing page (`app/page.tsx`) loads cleanly, and clearly
note to the user that the authenticated dashboard flow was not runtime-verified.

## Step 6 — Report

Summarize: which packages were updated (`Current` → new version), which were deferred and why,
the result of lint/test/build, and what was confirmed in the browser (including whether the login
flow itself was exercised).
